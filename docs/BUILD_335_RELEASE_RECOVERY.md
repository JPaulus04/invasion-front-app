# Build 335 release recovery

Main 5b0ce84ff36ecdea64a2e5e172624cc0e0359e08 failed validation run 43434500196 because moving seed 336/batch 2 exhausted both startup attempts. Both retained device snapshots show no OutpostZero process, no crash report, no PID reply and zero-byte app stdout/stderr. This was unexecuted gameplay, not a passing campaign or a real combat defeat.

The system logs show placeholder and installed LaunchServices registration after launch was requested. In attempt 1, launch was requested at 08:48:07 Eastern; the installed registration was observed around 08:49:08. In attempt 2, launch was requested at 08:53:18 and registration was observed around 08:53:38. `get_app_container` had returned before either launch. A filesystem container and a responsive launchctl therefore did not establish that app registration had settled. The old evidence does not establish every internal reason for the launch RPC stall, but it establishes this ordering gap.

TestFlight run 43449297391 correctly failed `release-gate` on the failed main validation. Its upload job was skipped. The release gate must not be bypassed or satisfied with unexecuted gameplay.

The correction adds a read-only `simctl appinfo` registration check after installation/container lookup and before any seeded QA app launch. macOS plutil parses the returned OpenStep plist. Matching bundle ID, executable and User application type are required; explicit placeholder entries are rejected. Two consecutive valid samples five seconds apart are required. Every poll is retained. The readiness phase has a 180-second monotonic deadline, with requests capped at 20 seconds and plist conversion at 10 seconds. Missing, malformed, placeholder, wrong-identity or unresponsive metadata fails closed. The existing two-device startup limit and cleanup fence still apply.

No app launch or reinstall occurs in the registration poll. Any actual QA output still latches the campaign into observation, and failed or incomplete gameplay is never retried. App source, seeds, replay checks, gameplay acceptance and TestFlight gates are unchanged. All six cases must execute and meet the original assertions in PR validation; the old failed main run remains failed. PR success does not authorize merge or upload, and a future approved merge still needs successful validation for its exact main SHA before the release gate can pass.
